# Hangar gap audit and plan — 21 September 2026 (B5)

> **Status: the plan in §3 was executed the same day.** See
> [`todo/2026-09-21.md`](../todo/2026-09-21.md) for what shipped and what is
> still open. This document is kept as written — it is the evidence that
> produced the plan, and the measurements in it are what the thresholds in
> `src/lib/image-quality.ts` are calibrated against. Two things in it turned out
> to be wrong and are marked ⚠️ below.

This is a walk of the console that is actually running on this Mac
(`launchd` → `next start` on :8003, build `b4c8d5hr…` from 10:02 today, which
is HEAD `7db29ef`), driven in a real browser, with every claim below checked
against a live call or a file on disk. Evidence images are in
`screenshots/gap-audit-2026-09-21/` (git-ignored).

The short version: **text, speech and the operator surfaces work; every image
this machine has produced through Hangar since 20 September is noise, and the
console currently hides that behind a "paused" card instead of fixing it.**
The rest of this document is the evidence, the other gaps the walk turned up,
and a plan for making Hangar the best local-AI experimentation system that
runs on most machines rather than on these two.

## 2. The gaps, ranked by how much they block "experiment locally with AI"

### Gap 1 — Image generation produces pure noise, and has since 16–20 September

**What you see:** Image Studio → *Create* shows an "Image setup" card: "Direct
generation in this page is paused because its current command-line connection
returns corrupted images." There is no prompt box. The only actions are *Open
Draw Things*, *Find image models*, *View saved images*.

**What is actually happening:** the images are not corrupted files. They are
structurally perfect PNGs (signature, every chunk CRC, IEND all valid) whose
pixels are high-frequency colour static. Every path was exercised today:

| Path | Result | Time |
|---|---|---|
| `local-ai image` (the CLI wrapper, `--offline`, 512², 4 steps) | noise | 1.9 s (model warm) |
| `draw-things-cli generate` **without** `--offline` (fresh recommended settings) | noise | 2.0 s |
| adapter `POST :8111/generate` | noise | 4.7 s |
| console `POST /api/image/generate` (model `draw-things-flux2-klein`) | 200, noise saved to `generated/`, gallery count 3 → 4 | 4.1 s |

So the console pipeline, admission control, saving and request logging all
work. The **engine** is what is broken, and it is broken at the Draw Things CLI
binary, not in Hangar:

| Date | Event | Output |
|---|---|---|
| 2 Sep | macOS 26.6.2 installed | — |
| 3 Sep 23:41 | `flux-local-smoke-test.png` from the same CLI | **real image** (red mug, notebook, window) |
| 12 Sep | `draw-things-cli 26.0910.1` published upstream (Homebrew) | — |
| 16 Sep 05:54 | **macOS 27 installed** (`softwareupdate --history`) | — |
| 20 Sep 19:46–20:10 | three console generations (paper airplane, pear, horse) | **noise** |
| 20 Sep 19:53 | the **Draw Things app** exported the same pear prompt | **real pear** |
| 20 Sep | commit `ef8a913` adds the "paused" card | — |
| 21 Sep | four fresh runs above | **noise** |

The installed CLI is the July build (`~/LocalAI/bin/draw-things-cli`, reports
`--version` = `dev`, SHA pinned in `~/LocalAI/config/runtimes.json` to release
`1.20260716.0`). The app on the same engine version renders correctly. The
only thing that changed on this box between a working CLI and a broken one is
the OS. The likeliest cause is a Metal/compute change in macOS 27 that the
July CLI mishandles and the app does not, and a CLI release that post-dates
the setup exists and has not been tried.

**Two cheap ways to confirm, neither done yet because both change something
outside the repo:**

1. Upgrade the CLI and re-run the same 512² prompt:
   ```bash
   brew install draw-things-cli        # 26.0910.1; or drop the release binary into a scratch dir first
   draw-things-cli generate --model flux_2_klein_4b_i8x.ckpt --prompt "a red mug on a desk" --width 512 --height 512 --steps 4 --cfg 1 --output /tmp/t.png --disable-preview
   ```
2. Enable the app's own server (Draw Things → Settings → gRPC server, default
   port 7859; the HTTP API is 7860) and point the same CLI at it with
   `--remote --remote-url 127.0.0.1 --remote-port 7859 --no-remote-tls`. The
   app is known-good, so this isolates the standalone binary.

Whichever passes becomes the engine the adapter uses. Sources:
[draw-things-cli announcement](https://releases.drawthings.ai/p/draw-things-cli-local-media-generation),
[26.0910.1 on Homebrew](https://github.com/Homebrew/homebrew-core/pull/306591),
[community releases](https://github.com/drawthingsai/draw-things-community/releases),
[gRPC/HTTP ports](https://github.com/wysie/drawthings-grpc-hermes-plugin).

**The deeper defect this exposes:** nothing in the stack looks at the output.
`local-ai`'s Sep 3 verification recorded `visually_inspected: true` by hand;
the adapter returns whatever bytes the CLI wrote; `generateAndSave` saves any
200 as a success; the gallery shows it with a latency badge; Requests logs it
as `200`. A model that emits static is indistinguishable from one that works,
all the way up to the UI. That is why this went unnoticed for four days and
why the fix in §3 includes an output check, not just a new binary.

### Gap 2 — Image Studio on this Mac is a dead end, by construction

- `src/components/qwen-tab.tsx:106` — `const isMacHost = getHostId() === "b5"`
  swaps the whole studio for the placeholder. It is keyed to one hostname, so
  any other Mac gets the full studio pointed at an adapter it may not have,
  and this Mac cannot get the studio back without a code change.
- The Home composer's Image mode stores the prompt
  (`home-cockpit.tsx:461`, `localStorage["bt-qwen-draft"]`) and navigates to
  `#qwen`. Verified: the draft is written, the tab opens, and the placeholder
  never reads it. **The prompt is silently dropped.**
  ⚠️ **Correction:** the studio *does* consume the draft correctly
  (`qwen-studio.tsx:333`). The placeholder replacing the studio was the entire
  cause, so removing the gate fixed the draft with no other change.
- *View saved images* switches to *Activity*, which reads `/api/qwen/archive`
  (`qwen-activity.tsx:73`). Nothing on this box writes there
  (`image-gen.ts:163` mirrors only when `target === "comfyui"`), so it says
  **"No images yet"** while `/api/qwen/images` returns four. The gallery that
  does hold them lives inside the studio the placeholder hides.
- *Find image models* jumps to Models with the `image` filter. The only local
  result is `local-flux2-klein-4b-draw-things`, badged **ready**, aliased as
  `openai/flux2-klein-4b-draw-things`. So the escape hatch loops back to the
  same broken model, labelled healthy, under a misleading provider prefix.
- *Open Draw Things* works, and is the only path that produces a real image.

### Gap 3 — Two galleries, two on-disk roots, one of them always empty here

`generated/` (studio gallery + DuckDB `images` table) and `archive/`
(Activity feed) are separate stores with separate APIs, separate file
serving, and separate metadata sidecars. On BeTenshi both fill because the
Qwen and ComfyUI services write the archive; on any host without those
services Activity is permanently empty. There should be one store and one
feed with a source/folder filter.

### Gap 4 — Requests cannot answer "what did that image/chat request do?"

Observed after the calls above:

- The chat row: target `ollama`, `200`, `6996 ms`, caller — and `model`,
  `prompt`, `response`, `tokensIn/Out` all `null`, although `/api/chat`
  returned all four. The image row likewise has no `model`, no `prompt`, no
  `artifact`. The detail panel says *"Not previewed — re-sending a POST could
  repeat the action."* Only the AI Router's LiteLLM callback ever filled those
  fields, and there is no router on a Mac.
- The feed is an in-process ring (`traffic.ts`, `globalThis.__hangarTraffic`,
  2000 events). It resets whenever the console restarts; the first thing seen
  today was "No requests captured" although the machine had generated images
  the evening before. Only router calls are persisted (DuckDB `router_calls`).
- The MODELS breakdown reads "No data" for the same reason.
- Three native `<select>` elements (`requests-view.tsx:154`, `:438`, `:478`)
  — the workspace standard forbids these.

### Gap 5 — Video Studio is wired to the same broken binary

`video-studio.tsx:57` shows an amber note ("smoke test produced undecoded
frames") but leaves the Generate button live and the `local-wan2-2…` model
badged **running**. A click would spend minutes producing garbage.

### Gap 6 — First paint tells the wrong story on every reload

For 2–3 s after any load, Home reads *Telemetry unavailable · 0.0 / 128.0
GB · 0 ready now · 0 on demand* and "Can it run?" says *Cold start required*
— then the numbers arrive. The same flash appears on mobile. These are
default values rendered as facts; they should be skeletons. Related, and
already noted in `todo/2026-09-14.md`: `useLiveRefresh` freezes while the tab
is hidden, so a backgrounded console never updates.

### Gap 7 — Two surfaces disagreed about whether the model was resident

At 13:50 Home said *Model to load: Already resident · Startup: Ready now*
for Chat & Code. At 13:56 `ollama ps` was empty and the LLM tab said
*ready to load · idle 0 MB*. Ollama's keep-alive may have unloaded it in
between, which is exactly why residency needs one source of truth with a
timestamp, not two components each inferring it.

### Gap 8 — Portability: the code still knows these two machines by name

The README's thesis is "adding a machine is adding a JSON file", and the
profiles do most of that. But:

- `host.ts:157` — any Darwin host without a matching profile becomes `b5`;
  `:138` — anything else becomes `betenshi`. A stranger's Mac is told it is B5.
- Hard `b5` gates: `qwen-tab.tsx:106`, `video-studio.tsx:57`,
  `image-models.ts:96` (`APPLE_HOST`), `providers.ts:633` (`B5_DEFAULTS`).
- Absolute paths: `scripts/local-ai-adapter.mjs:18` and `:57`
  (`/Users/alibadereddin/…`), `scripts/service-commands.b5.json`.
- The image service is still called `qwen` because the studio routes on that
  id; the adapter fakes a Qwen-Image health shape to fit.
- `scripts/detect-host.mjs` on this box: does not know port 8111 ("2 of 14
  known ports"), flags 8021 as unidentified (something is bound there and
  answers nothing), and drafts `qwen3-vl:32b-instruct` as the text default
  simply because it is first in `ollama list` — not the 27B the profile uses.
- `.claude/skills/hangar-setup` stops at "one working local LLM". There is no
  setup path for image or speech on any OS, and Ollama (the only installer
  wired in, commit `7db29ef`) cannot run image models.
- Arena and Usage require the AI Router, which does not exist on a Mac, so
  two of the thirteen tabs are permanently inert here.

## 3. The plan — Hangar as the local-AI experimentation system for most machines

### Principles

1. **A capability is verified by its output, never by a 200.** An image is
   an image if it is not noise; a WAV is speech if it transcribes back; a
   transcript is a transcript if it matches a known clip. Health checks stay,
   but the UI's "ready" badge comes from the last verified run.
2. **Engines are drivers behind a contract.** Text/vision/embeddings via
   Ollama everywhere; image, speech and video via a small adapter interface
   with one driver per engine. Hangar never depends on one binary.
3. **Declared, not inferred, and portable.** Profiles declare drivers and
   paths; nothing in `src/` mentions a hostname; nothing outside a profile
   mentions a home directory.
4. **One history.** One durable store for requests and one for artifacts,
   with views over them, instead of rings and mirrors.

### Phase 0 — unblock images on this Mac (days)

1. Confirm the engine fix: try CLI 26.0910.1; if still noise, enable the app's
   gRPC server and use `--remote`. Record which one passed in
   `~/LocalAI/config/runtimes.json` and the host profile.
   ⚠️ **Outcome:** CLI 26.0910.1 does not work either — it crashes with
   `use of undeclared identifier 'matmul2d_descriptor'`, a Metal 4
   cooperative-tensor shader this machine's Metal compiler rejects. That is the
   same root cause as the older build's silent noise. Neither CLI version is
   usable here, so the driver became **mflux** (FLUX.2 Klein on MLX), which is
   a different compute stack and was verified working the same afternoon.
2. Add an **output sanity check** in the adapter and in `generateAndSave`:
   reject an image whose Laplacian variance / high-frequency energy is that of
   static, and optionally ask the local vision model "describe this in five
   words" and refuse a description of noise. A rejected image is a 502 with
   the reason, not a saved success.
3. Remove the `b5` gate in `qwen-tab.tsx`; gate on the profile instead
   (`image.verifiedAt` present → studio; absent → setup card that still shows
   the prompt box and the draft from Home).
4. Make the studio read `bt-qwen-draft` on mount.
5. Point *View saved images* at the gallery that has images; fold Activity
   into it as a filter.
6. Disable Video's Generate button while its engine is unverified.

### Phase 1 — the portable core: capability contracts and drivers (weeks)

Profile schema gains a `runtimes` block, one per capability:

```json
"runtimes": {
  "text":  { "driver": "ollama",       "model": "qwen3.8:27b-mlx" },
  "image": { "driver": "draw-things",  "transport": "grpc", "model": "flux_2_klein_4b_i8x.ckpt", "verifiedAt": "2026-09-22T…" },
  "stt":   { "driver": "mlx-audio",    "model": "qwen3-asr-1.7b-8bit" },
  "tts":   { "driver": "mlx-audio",    "model": "qwen3-tts-1.7b-customvoice" }
}
```

Drivers, by platform (the ones in bold already have working code paths here):

| Capability | Apple silicon | NVIDIA (Windows/Linux) | CPU-only / AMD |
|---|---|---|---|
| Text, vision, embeddings | **Ollama** | **Ollama** or **vLLM** | Ollama |
| Image | **Draw Things** (app gRPC/HTTP, or CLI), or [mflux](https://github.com/wesbiggs/mfluxible) / [MLX klein weights](https://huggingface.co/collections/mlx-community/flux2-klein-mlx) as a pure-Python fallback | **ComfyUI** (klein 4B, Z-Image, HiDream already wired) | ComfyUI CPU or cloud via router |
| Speech → text | **mlx-audio Qwen3-ASR** | **Whisper** service | whisper.cpp |
| Text → speech | **mlx-audio Qwen3-TTS** | **Kokoro** / Chatterbox | Kokoro CPU |
| Video | Draw Things Wan 2.2 (optional) | ComfyUI (optional) | — |

The `qwen` service id and the fake Qwen-Image health shape go away; the
studio routes on `runtimes.image`. Split the Mac adapter into one process per
capability so stopping speech does not stop images.

### Phase 2 — setup that proves itself (weeks)

- `node scripts/doctor.mjs`: for every declared runtime, run the smallest real
  job (256² image, one-sentence TTS, 5 s STT, one chat token) and **check the
  output**, then write `verifiedAt`. The UI badges come from this.
- Extend `hangar-setup` past the LLM: detect Draw Things / ComfyUI / mlx-audio
  / whisper, offer to install the one that fits (`brew install draw-things-cli`,
  `pipx install mflux`, ComfyUI portable on Windows), always with approval,
  always followed by the doctor run.
- `detect-host.mjs`: learn 8111 and 8021, prefer the profile's or the largest
  chat-capable model rather than the first tag.
- Replace the darwin→`b5` fallback with "no profile" + the setup card.

### Phase 3 — observability that survives a restart (weeks)

- Every `withTraffic` route records what it knows: `/api/chat` has model,
  prompt, response, tokens; `/api/image/*` has model, prompt, seed and the
  saved file. Write them to DuckDB alongside `router_calls`; keep the ring
  only as a hot cache.
- Requests detail renders the artifact and the response; MODELS breakdown
  works on a router-less host.
- One artifact store (`generated/`) with source tags; Activity becomes a
  filter on it.
- Replace native selects with the project `Select`; render skeletons on first
  paint; keep refreshing at a slow cadence when hidden.

### Phase 4 — later

- Fleet view across registered hosts (the "Also yours" row is the seed).
- Optional local router (LiteLLM) so Arena and Usage are not dead on a Mac,
  or make those two tabs work directly against Ollama.

### What "most machines" means

| Machine | Text | Image | Speech |
|---|---|---|---|
| 8 GB laptop, any OS | 4B-class via Ollama | cloud through router, or none | whisper.cpp small |
| 16–32 GB Mac | 8–14B | FLUX.2 klein 4B (≈12 GB) | mlx-audio |
| 64–128 GB Mac (this one) | 27–32B + vision | klein 4B, Wan 2.2 video | mlx-audio |
| NVIDIA 8–12 GB | 8B | klein 4B via ComfyUI | Whisper + Kokoro |
| NVIDIA 24 GB+ (BeTenshi) | 27B+ | klein / Z-Image / HiDream | all |

### Done means

On a fresh Mac, Windows or Linux box: `/hangar-setup` → within 30 minutes
chat, an image and a spoken sentence have each been produced **and verified**,
every one appears in Requests with its prompt and output, and no tab says
"ready" for anything that has not passed the doctor.
