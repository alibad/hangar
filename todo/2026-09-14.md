# 2026-09-14

## What We Built

**The console now knows which machine it is on.** One codebase runs BeTenshi
(Windows, RTX 5090) and B5 (MacBook Pro, M5 Max, 128 GB unified memory) and
behaves correctly on each, instead of needing a fork per box.

- Open it on B5 and it calls itself B5, shows a single **Memory (unified)** bar
  rather than VRAM plus a separate System RAM section, reports GPU utilisation
  from Apple's own counters, lists Ollama as the LLM service, and hides the
  Image / 3D Body / Segment / Speech tabs whose services only exist on BeTenshi.
- Open it on BeTenshi, or on Vercel, and nothing changes: same service list,
  same `nvidia-smi` probe, same PowerShell RAM attribution, same public URLs.
- The Service Manager is host-aware too. On B5 it finds Ollama already running
  under the menu-bar app and offers to adopt it, exactly as it does for a
  hand-started service on BeTenshi.

## What We Fixed

- **The manager's service list had drifted from the console's.** It carried its
  own hand-copied array, with vLLM on :8000 while the console had moved it to
  :8005. Both now read the same `config/hosts/<id>.json`; the drift cannot recur.
- **Free memory was wrong on macOS.** `os.freemem()` reports only literally-free
  pages there and ignores tens of GB of reclaimable cache, so the fit check would
  have refused every model on a box with 55 GB available. The probe now reads
  `vm_stat` on Darwin and stays `os.freemem()` on Windows.

## Key Decisions

**Profiles are JSON, not TypeScript.** It costs the inline comments the old
registry had (they moved to `note` fields) and buys one file that both the Next
app and the CommonJS manager can read. That is what kills the duplication.

**The host is resolved once, in `next.config.ts`, and published as an env var.**
Two client components import the service registry, and a module that touches
`os` cannot be bundled for the browser. One string, read the same way on both
sides, sidesteps the whole server/client split.

**Unknown host means BeTenshi.** A Vercel build box is Linux with a random
hostname. Falling back anywhere else would silently retarget production.

**Unified memory is a first-class model, not a special case of discrete.** The
existing footprint logic adds VRAM and RAM because on BeTenshi they are separate
budgets. On B5 they are the same 128 GB, and the profile says so, so the UI
labels one bar and the Ollama footprint carries the same number on both sides
with a `basis` explaining why.

## Not Done

- The Windows path is preserved by keeping its code byte-for-byte and gating the
  new branches behind the profile; it has not been executed on BeTenshi since.
- The LLM tab talks to one Ollama model (the profile default). Switching among
  the pulled checkpoints is a `model` field away but has no UI yet.
- B5 has no AI Router, so the Models tab honestly reports the router offline.

## Rebased onto the redesign

Upstream had moved 27 commits while this was built: a console redesign, a
resource coordinator in the manager, Windows per-process GPU counters in the
GPU route. Rather than resolve seven conflict-marker files, the change was
re-applied on top of the new tree:

- The coordinator's capacity reader is host-aware. On an NVIDIA host it still
  asks `nvidia-smi`; on a unified-memory host it reports the system pool as the
  GPU budget, so admission checks a model's footprint against a real number
  instead of an imaginary empty card. `config/resource-policy.json` gained an
  `ollama` entry pointing at the `local-ollama` footprint.
- The Windows GPU performance-counter path is kept verbatim and gated to
  `platform === "win32"`; every other host gets an empty list and the bar falls
  back to service self-reporting.
- The redesign's `ResourcePulse` and `HomeCockpit` carried their own GPU types
  with non-null temperature and power, and rendered "0°C · 0W" when absent. They
  now hide those metrics, and the pulse shows one Memory meter on a unified host
  instead of GPU and RAM meters that would be the same number twice.

## Two more things the rebase surfaced

- **The console needs Node 22.** Upstream's scout imports `node:sqlite`, which
  does not exist in Node 20, and `next build` dies collecting page data for
  `/api/scout` with `ERR_UNKNOWN_BUILTIN_MODULE`. Vercel builds on 22 so it never
  showed there; a Node 20 machine fails silently at build. Pinned with `.nvmrc`
  and `engines` so the mismatch is named instead of guessed at.
- **The scout's machine profile bypassed the host.** `src/lib/machine.ts` called
  `nvidia-smi` directly, so on B5 it reported "No CUDA GPU detected, 0 GB" and
  every local model as not fitting on a box with 128 GB to spare. It now reads
  the same host probes as the GPU route.

## Corrected: show the whole UI everywhere, and warn

The first pass HID what a host could not back — tabs, workstreams, composer
modes. That was the wrong instinct and it was called out: a console that shows a
different set of surfaces per machine reads as two apps sharing a name, and it
conceals the one thing you want to know, which is what this box cannot do.

The rule now: **every surface exists on every machine; availability is shown,
never used to remove.**

- All tabs render on all hosts. A tab with nothing behind it here shows a notice
  naming the services it needs and where they are declared, instead of a view
  that would spin, error, or return empty.
- The Workstreams menu lists all six, with a "not on this machine" badge on the
  ones this host cannot back.
- All four Home cards render. The status pill reads "Not on this machine" in
  amber beside Ready / On demand, and the VRAM cell says what is missing
  ("needs qwen") rather than quoting a profile the host cannot honour.
- Workstreams went back to four canonical definitions in the component; a host
  profile now supplies OVERRIDES only where that machine genuinely differs (B5
  backs Chat & Code with Ollama rather than vLLM).

What still differs per machine is only what is real: the machine's name, its
service list, whether memory is one pool or two, and which tool reads the GPU.
On BeTenshi every workstream is backed, so nothing is marked and its UI is
unchanged.

Verified on B5: thirteen surfaces present, four menu badges, three card pills
(needs qwen / whisper / sam3), one unified Memory meter.

## The redesign's own surfaces were still BeTenshi-only

Adapting the older views was not enough. The redesign added a Home page that
hardcoded this box's capabilities, so on B5 it advertised work the machine
cannot do:

- **`workflowConfig` in `home-cockpit.tsx`** listed four workstreams — Chat &
  Code, Image Studio, Speech, Vision & 3D — with BeTenshi service ids, model
  names and VRAM figures baked in. Three of the four pointed at services that do
  not exist on B5, each linking to a tab that was already hidden. Workstreams are
  now declared per host in `config/hosts/<id>.json`; BeTenshi keeps all four
  verbatim, B5 declares one (Chat & Code on Ollama). Icons stay in code because a
  component cannot be serialised.
- **`ConsoleHeader` kept a SECOND hardcoded list** for its Workstreams menu, so
  even with the cards fixed the menu still offered Image Studio, Speech, 3D Body
  and Segment. Both that menu and the tab bar now use one rule, `hostHasTab()`,
  resolved from the build-time profile — which also removes the flash of tabs
  that appeared and then vanished once `/api/host` answered.
- **`31.8` and `63.3` were hardcoded fallbacks** in `resource-pulse.tsx` and
  `home-cockpit.tsx`, so before telemetry arrived a Mac showed BeTenshi's card
  size and RAM. Each host now declares its own totals.

Verified on B5: header reads B5, one unified Memory meter at 51.7 / 128.0 GB,
"Can it run?" predicts against qwen3.8:27b-mlx at 18.2 GB, and exactly one
workstream is offered.

**Not a bug, worth recording:** the console appears frozen in an automated
browser because `useLiveRefresh` deliberately pauses while `document.hidden`.
A headless or background tab fetches nothing until it is fronted or Refresh is
clicked. Two rounds of "the data is not loading" were this.
