# 2026-09-15 — B5: the vision capability, and a console that stays up

Picked up six commits from BeTenshi (through `ea54d98`), adapted what the Mac
needed, and fixed what the merge exposed.

## What We Fixed

**The Vision capability offered nothing — on either machine.** BeTenshi's fix for
"Vision offers every chat model and routes to a 7B that cannot see" shipped in two
halves, and only one landed: `modelsFor("vision")` began filtering on a declared
`vision` flag, but no entry in `config/model-meta.json` ever carried one. All 24
entries, zero flags, so the filter removed the entire catalogue. It failed
silently because an empty capability looks exactly like one whose models are all
stopped. Nine aliases now declare it, and there is a test that fails if they stop.

**`local-qwen3-vl` answered with an empty string.** The router alias pointed at
`qwen3-vl:32b`, which is the *thinking* variant — Ollama's `think: false` does not
disable its reasoning; it spends the whole budget in the `thinking` field and
returns `content` empty. In the bench it burned 321–544 tokens on a 119-character
answer, then hit the 600 s timeout on the second card and stopped. Repointed to
`qwen3-vl:32b-instruct`, which finished all ten. **This needs `ollama pull
qwen3-vl:32b-instruct` on BeTenshi** — it was pulled and measured on B5, and that
box's store was not checked. Until then the alias 404s, which is the loud failure
the empty string was not.

**`local-gemma4` and `local-qwen3-vl` had no metadata at all.** Both were routed
but carried no footprint, so the fit engine could not price them. Added with the
2026-09-14 bench numbers, and with the basis stated — including that Gemma's
19 GB is B5's `mlx` sibling rather than BeTenshi's `it-qat` build, which nobody
has measured.

**Three orphaned consoles on three different ports.** 8013, 8014 and 8015, each
serving whatever the code said when it started, none on the port anyone was
looking at. That is how a stale UI gets mistaken for missing features — which is
exactly what happened yesterday. Killed, and replaced with one supervised
instance.

**The docs described the design that was rejected.** `AGENTS.md` still said the UI
"hides tabs whose services are not registered on this host". It does the opposite
now, and the rule is written down with the reason.

## What We Built

**The console starts itself on B5 and stays up.** A launchd agent
(`scripts/com.betenshi.console.plist`) runs `scripts/start-console.sh`, the Mac
sibling of `start-console.ps1`: fixed port **8003** — the same address as
BeTenshi, because it is the same product — with `RunAtLoad` and `KeepAlive`, log
rotation into `var/console.log`, and Node resolved explicitly to 22 (launchd runs
no login shell, so nvm is never sourced, and `/api/scout` imports the
Node-22 builtin `node:sqlite`). Verified: killed the server, launchd had it
answering 200 on 8003 again inside 35 s.

**The manager autostarts too, and that was the bigger half.** The console alone
is not enough: with nothing on :8099, `/api/resources` answers "Manager error:
fetch failed" and the whole top of Home degrades at once — Machine capacity reads
"Telemetry unavailable" at 0.0 / 128.0 GB, the ready counts sit at zero, and
every workstream shows "On demand" however resident its model is. It does not
look like a missing supervisor; it looks like an empty box. `com.betenshi.manager`
now runs `scripts/start-manager.sh` under the same rules. With it up, Home reads
what it should: B5, one unified Memory bar at 59.0 / 128.0 GB with healthy
headroom, 1 ready / 1 on demand, and Chat & Code already resident.

**The header called B5 "BeTenshi" until data arrived.** `hostName` comes from
`/api/host`, so it is undefined on first paint — and on a background tab it stays
undefined, because the live refresh pauses while `document.hidden`. The fallback
was a hardcoded literal, so the one surface whose job is to say which machine you
are looking at was showing the other machine's name. It reads `getHost().name`
now, which needs no fetch: the id is resolved at build time into
`NEXT_PUBLIC_HOST_ID`.

## Key Decisions

- **Declaration beats inference, but is no longer the only source.** `vision` now
  falls back to LiteLLM's own `supports_vision` when nothing is declared, so a
  cloud model added later still lands in the right capability. The declaration
  still wins — it is the only possible source for a locally-served model, and the
  only way to pin a text-only one to `false`.
- **The router was left off B5.** `litellm` is not installed here, so Models and
  Arena report "router not running" rather than crashing (verified). Installing it
  is a real decision — a Python dependency and a B5-specific model list — not a
  gap to quietly fill.

## Known Consequence

A console that is always running now holds the DuckDB lock on
`~/betenshi/betenshi.db`, so `npm run build` logs a "Conflicting lock is held"
error while collecting page data. The build still exits 0 and the route catches
it — but if that noise ever needs to be gone, stop the agent first:
`launchctl bootout gui/$UID/com.betenshi.console`, build, then bootstrap it back.

## Breaking Changes

None to the UI. One runtime prerequisite: **BeTenshi needs `ollama pull
qwen3-vl:32b-instruct`** before `local-qwen3-vl` will answer.
